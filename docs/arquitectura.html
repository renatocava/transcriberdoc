1. Resumen

MedScribe es una aplicación web de una sola página escrita en Python con Streamlit. El médico graba la consulta en el navegador; el servidor envía el audio a OpenAI para transcribirlo y separar a los hablantes, y luego envía la transcripción a Anthropic (Claude) para llenar una historia clínica estructurada, con la fuente de cada dato y los códigos CIE-10 validados contra el catálogo oficial del MINSA. El médico revisa, corrige y guarda.

Toda la inferencia de IA ocurre en APIs externas. El servidor solo orquesta, valida y muestra la interfaz, así que el hardware que necesita es modesto (ver sección 7).

2. Vista de capas

El código se organiza en un punto de entrada (app.py), una capa de pantallas (components/) y una biblioteca sin interfaz (lib/). Las pantallas dependen de lib, nunca al revés, salvo lib/state.py, que encapsula st.session_state.

4. Flujo de procesamiento de una consulta

  1. Captura del audiorecording recibe el audio del micrófono (webm/Opus), del archivo de demo o de un archivo subido y lo guarda en session_state. Pasa a processing.
  2. Transcripción con diarizacióntranscription envía el audio y, si hay médicos elegidos, sus muestras de voz a OpenAI. Devuelve intervenciones {speaker, text, start, end}. 15–40 s para una consulta de 2–3 min, contando también la extracción.
  3. Asignación de roleshablantes.mapping_inicial asigna Doctor / Paciente / Acompañante según el modo elegido y las voces reconocidas por nombre.
  4. Extracción estructuradaextraction envía a Claude el diálogo numerado con roles y el JSON Schema de schema + fuentes. Claude responde obligatoriamente con el tool.
  5. Validaciónschema.normalizar_historia completa la estructura, cie10.validar descarta códigos inexistentes o dados de baja y fuentes.vincular ancla cada dato a sus intervenciones.
  6. Revisiónreview muestra transcripción y formulario. Si el médico corrige roles, se repite el paso 4 (se pierden las ediciones). Editar el formulario no vuelve a llamar a las APIs.
  7. GuardadoSe quitan las claves internas (_uid, _fuentes) y el JSON final se imprime en la consola del servidor. No se escribe en ninguna base de datos.

5. Máquina de estados

La etapa vive en st.session_state["stage"]. Solo hay st.rerun() al cambiar de etapa, al re-extraer y al guardar o descartar.

7. Requisitos de hardware

Como la transcripción y la extracción corren en OpenAI y Anthropic, el servidor no necesita GPU ni mucha CPU: pasa la mayor parte del tiempo esperando respuestas de red. La memoria crece con las sesiones abiertas, porque cada una guarda su audio y su transcripción en RAM.

Servidor — mínimo

Demo con 1–3 usuarios a la vez

  • CPU: 1 vCPU x86-64 o ARM64
  • RAM: 1 GB
  • Disco: 2 GB libres (entorno virtual ~0,5 GB + código y datos ~5 MB)
  • GPU: no se usa
  • SO: Linux, macOS o Windows con Python 3.11

Servidor — recomendado

Uso en clínica, hasta ~10–15 consultas simultáneas

  • CPU: 2 vCPU
  • RAM: 2–4 GB
  • Disco: 10 GB SSD (registros, voces y margen para actualizaciones)
  • GPU: no se usa
  • SO: Linux (p. ej. Ubuntu 22.04/24.04 LTS) con systemd y un proxy HTTPS (Caddy o Nginx)

Equipo del médico (cliente)

  • Navegador moderno: Chrome/Edge 100+, Firefox 100+ o Safari 15+
  • Micrófono (integrado, USB o de solapa). Para consultas con paciente conviene uno omnidireccional o de conferencia cerca de ambos
  • 4 GB de RAM o más; cualquier CPU de los últimos ~8 años
  • Pantalla de 1366 × 768 o mayor: la revisión usa dos columnas
  • Parlantes o audífonos para reproducir las citas de audio

Red

  • Salida HTTPS (puerto 443) desde el servidor hacia api.openai.com y api.anthropic.com
  • Subida del cliente al servidor: ~0,5–2 MB por consulta de 2–3 min (webm/Opus); el límite de la API es 25 MB por audio
  • 1 Mbps simétrico basta por consulta; la latencia la dominan las APIs, no el enlace
  • Sin internet: solo funciona el modo simulado (USE_MOCK = true)

8. Red, despliegue y seguridad

  • El micrófono exige contexto seguro. El navegador solo entrega el micrófono en HTTPS o en localhost. Si el servidor se abre por una IP de red local con HTTP, la grabación falla en silencio. En un servidor propio hace falta un proxy HTTPS delante de Streamlit (puerto 8501 por defecto) que también reenvíe WebSocket.
  • Un proceso, muchas sesiones. Streamlit atiende todas las sesiones en un solo proceso Python; cada consulta en curso bloquea solo su propia sesión mientras espera a las APIs.
  • Arranque automático. En Linux, un servicio systemd con las API keys como variables de entorno (lib/config.py las lee si no hay secrets.toml).
  • Datos clínicos. El audio y la transcripción salen hacia OpenAI y Anthropic. Las muestras de voz son datos biométricos y quedan en voces/: respáldalas y restringe sus permisos. La historia «guardada» queda en los registros del servidor, que deben tratarse como información clínica.
  • Streamlit Community Cloud. El despliegue actual funciona sin hardware propio; allí el disco se borra al reiniciar, así que las voces registradas no persisten.
